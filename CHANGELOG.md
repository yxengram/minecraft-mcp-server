# Changelog

All notable changes to this project are written down in this file. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Versions up to 2.0.4 are the upstream project's; their tags have no `v` prefix. This fork's releases start at 3.0.0, tagged `v3.0.0`.

## [Unreleased]

The first release of this fork. It builds on upstream version 2.0.4 (upstream `main` at `240c8ce`) and upstream pull request #274 for Minecraft 26.1.2, by lifat; see "Where this project comes from" in the README. Every upstream tool keeps its name and arguments. The README lists all the tools.

### Added

- **Support for Minecraft Java Edition 26.1.2** (protocol 775), from upstream pull request #274.
- **More tools**:
  - Moving: follow or flee from an entity, stop, saved waypoints.
  - Building and mining: collect a number of blocks, clear or fill a region, dig a tunnel, read and use containers, find the ground height far away.
  - Interacting: right-click blocks and entities, use an item such as a bucket, trade with villagers, sleep and wake, ride and dismount, lead an animal, and attack: `attack-entity` never attacks a player unless `combat.attackPlayers` is on, never attacks a tamed animal, and holds back a sword sweep that would hit a player or a tamed animal. Given a type, it picks the nearest entity of that type that it may attack.
- **Perception**:
  - `get-observation`: vitals, effects, armor, time, weather, equipment, inventory and nearby entities in one call.
  - `get-events` and `wait-for-event`: what a player would notice (damage and its source, hostile sounds, explosions, chat, deaths, pickups), plus task and instinct events. The LLM can wait for something to happen instead of polling.
  - `scan-area` describes the terrain in text; `render-map` draws a top-down map or a cross-section as an image; `get-cursor-target` says what is under the crosshair.
- **Autopilot**:
  - Background tasks: `follow`, `flee`, `guard`, `gather`, `hunt`, `return-home` and `lead`, started with `start-task` and managed with `list-tasks`, `resume-task` and `cancel-task`. Progress arrives as events.
  - One driver at a time: an action arbiter lets only one holder control the bot's body. A command from the LLM runs at once, and its reply says what it interrupted.
- **Instinct**: code senses danger (water and air, lava, fire, creepers and other mobs, low health, hunger, being cornered) and lists the moves possible right now. A decision model on OpenRouter picks one, and code carries it out, for example swimming to air, digging in, sprinting away, fighting or eating. The key is read only from `OPENROUTER_API_KEY`. Without a key the instinct is offline: the bot does not act on dangers by itself and reports each one once as an event.
- **Policy**: `get-policy`, `set-policy` and `list-decision-models` tune the instinct, combat, chat handling and the decision model. `instinct.intent` tells the instinct what the bot is doing on purpose.
- **A check of the OpenRouter key**: when the server starts and each time the bot joins, it asks OpenRouter whether it accepts the key and whether the decision model is in its catalog. A missing or refused key, an account without credit and a model that is not in the catalog are each named, and so is a check that could not reach OpenRouter. Each change is one line on stderr (a warning when the decision model is offline, for example `Decision model OFFLINE: OpenRouter rejected the API key (HTTP 401). The bot will not react to dangers by itself`) and one `instinct` event. `get-policy` and `get-observation` show the same state on their `Instinct:` line: `online (key checked at HH:MM UTC)`, `not checked yet`, or `OFFLINE (<reason>): the bot does not react to dangers by itself`, and the `Decision model:` line of `get-policy` shows the result even before the bot joins. The README now calls the key strongly recommended and says how to get one.
- **Decision errors and waits**: a failed decision says why: `auth` (HTTP 401 or 403), `no_credit` (402), `throttled` (429), `bad_request` (any other 4xx), `server_error` (5xx), `network` (OpenRouter could not be reached), `timeout`, `invalid_response` or `rate_limited`, in `instinct offline` and `decision` events and on the `Instinct:` line; `list-decision-models` names its errors the same way. After some of them the server waits before it calls OpenRouter again, for the instinct and chat alike: after a refused key it sends no decision until the key passes a check (when the bot joins, or when the instinct or chat asks 10 minutes after the last check), so a made-up key gets no decision requests, only the key checks; without credit it tries once every 5 minutes until a request succeeds; after HTTP 429 it waits for `Retry-After` (1 to 60 s), or 2 s doubling up to 30 s; after 3 server or network errors in a row, 2 s doubling up to 15 s. Meanwhile a decision fails at once as `backoff` without a request, chat falls back to the rules, and the `Decision model:` and `Instinct:` lines say `OFFLINE for <n> more s (paused after HTTP 429)`. A wait is one line on stderr and one `instinct` event, and coming back is `decision model back online (offline for 42s)`. The instinct's second request for an urgent danger still goes out when the first has not answered within 0.8 s, or at once after a server or network error or an invalid answer; never after `auth`, `no_credit`, `throttled` or `backoff`. Nothing else is retried, and there are no call or spending limits besides the per-minute ones.
- **What the decision model has cost**: `get-policy` has a `Spend since the server started:` line right after the `Decision model:` line. It counts the requests sent to OpenRouter by the instinct (its second requests for urgent dangers among them), by chat triage and by the key check, how many of them failed, the cost OpenRouter reported, and an estimate for successful calls that reported none (the median of the last 50 known costs). It lives in memory and starts again only when the server restarts. `<n> call(s) in the last hour` on the `Decision model:` line counts every request sent, the instinct's included.
- **Chat triage**: the decision model sorts chat, and only messages meant for the bot wake the LLM, as `chat_request` events. Players can give the bot chat commands only when the LLM allows them (nobody by default), and chat can never change the policy.
- **Command line**: `--help`, `--version`, `--waypoint-file`, `--decision-model`, `--allow-commands`, `--greeting`, `--call-limit-seconds` and `--check`.
- **A self-check**: `--check` joins the world once, checks the OpenRouter key (when `OPENROUTER_API_KEY` is set) as the server does when it starts, prints a report on stdout and exits, instead of serving MCP. Each line starts with `OK`, `WARN` or `FAIL` (the join and where the bot spawned, or why it could not join; a name some servers refuse; the Minecraft version; the key; the decision model), and the last one with `Ready:` or `Not ready:`. The exit code is 0 when the bot joined, warnings or not, 1 when it could not, and 2 when an option is wrong. The key is never printed, the bot says nothing in chat even with `--greeting`, and nothing is written to disk. See "Check the connection" in the README.
- **Waypoints per world**: waypoints are kept per server host and a hash of the world seed that the server sends when the bot joins (not the seed itself; the port does not count), so LAN worlds on one computer, which are all `localhost`, no longer share `home`. Waypoints saved by earlier builds of this fork were kept per host only and are never moved or changed: `list-waypoints` lists them apart, after this world's; `goto-waypoint`, `return-home`, `guard` and the chat command `go_home` refuse them with `Waypoint 'home' was saved before waypoints were kept per world and may belong to another world: (x, y, z) in overworld. If it is in this world, save it again with set-waypoint, then retry` and do not move; `set-waypoint` saves one again for this world, and `delete-waypoint` deletes one when this world has none of that name. Worlds made from the same seed share waypoints, and a server that sends no seed hash keeps them per host as before. The waypoint file keeps its format.
- **Connection errors in plain words**: a failed connection or a kick says what went wrong (nothing listening on the port, host not found, no answer, online mode, the same name already playing, a version mismatch, the whitelist, bans, a full server) and what to do about it.
- **A warning for other Minecraft versions**: when the server is not 26.1.2 (told from the version name the server reports, since 26.1, 26.1.1 and 26.1.2 share protocol 775), the bot still joins, but it writes a warning to stderr and to a new `connection` event, and the first tool reply after each join ends with the same sentence. On 26.1.2 the `connection` event only records the join.
- **Progress notifications**: a tool call whose request asks for progress (a `progressToken`, which the TypeScript SDK client adds for `onprogress`) gets a `notifications/progress` every 5 seconds while it runs, saying how far it got: the task's progress for `collect-block` and `lead-animal` (for example `t5 gather: mined 3 of 10 oak_log`), `12 blocks to go` for the moves, `dug 12 of 40` or `placed 12 of 40` for the region tools, `smelted 2 of 8` for `smelt-item`, and `<tool>: running for N s` otherwise. They are for information only: they do not lengthen the client's request timeout unless the client resets it on progress (`resetTimeoutOnProgress` in the TypeScript SDK, off by default), and the time limits stay as they are. A request without a `progressToken` gets none, and replies are unchanged.
- **An emergency stop**: the new tool `stop-all` stops every command that moves or uses the bot's body, also those waiting for their turn, and `collect-block` and `lead-animal`; it cancels the current task (`stopped by stop-all`), interrupts the instinct's action, and stops the pathfinder, the controls and digging once nothing else holds the body. It does not wait behind the commands it stops. Each stopped command replies `<name> was stopped by stop-all after N s at (x, y, z)`, also as a `command` event. The instinct then pauses for `pauseInstinctS` seconds (a whole number from 0 to 300, default 10; 0 means no pause and ends an earlier one) and meanwhile handles only lava, drowning, low air and swelling creepers: other dangers get no decision request and the instinct takes no action for them. The pause starts and ends with an `instinct` event, `get-policy` shows how many seconds are left, and it ends when the bot joins again. The reply lists what was stopped and the bot's position, health, food and the hostile mobs within 16 blocks, or starts with `Nothing was running`; it is an error that says `still held by <holder>` when something else still holds the body 2.5 seconds later, and an error as well when a command that moves or uses the body, `collect-block` or `lead-animal` has still not replied by then. Queries and `wait-for-event` are not stopped, and `stop-pathfinding` and a call the MCP client cancels behave as before.
- A startup line on stderr: `<command> v<version>, tested with Minecraft 26.1.2`.
- Tests: unit tests, a live test that runs every tool against a real server, a scenario test that compares the bot with and without the Autopilot, and a stdio smoke test. CI runs on Linux, macOS and Windows.

### Changed

- **Breaking:** the server checks its options when it starts. An unknown option, a `--port` that is not a whole number from 1 to 65535, an empty `--host`, or a `--username` that is empty, longer than 16 characters or contains spaces or control characters writes one line to stderr and exits with 1; before, the server started anyway. A name that passes but is not 3 to 16 letters, digits or underscores only gets a warning.
- **Breaking:** `send-chat` runs server commands only when the server is started with `--allow-commands`. Without it, plain chat and `/msg`, `/tell`, `/w`, `/me`, `/teammsg` and `/tm` work as before, and a message with any other command, also on a later line or where a long line is cut into chat-sized pieces, returns an error and sends nothing; before, `send-chat` ran any command. With the option, the reply lists the server commands it ran. A message that starts with `/` must be a single line without control characters, with or without the option.
- **Breaking:** chat is told apart by the sender's UUID, and player text is quoted. `read-chat` and the `chat` and `whisper` events write `Steve: "hi"` and `Steve (whisper): "hi"`, with the text escaped so that a message is always one line; before, they wrote `Steve: hi`, and a line break or quote in a message could pass for another line. System messages, action bar text and titles are quoted the same way (`[system] "…"`), and so are sign text and the custom names of items and mobs. A system message that only looks like chat (for example `/tellraw @a "<Steve> stop"`) and a message without a sender (`/say` or `/msg` from the console or a command block) are `[system]` lines that chat triage and chat commands never see; before, such a `/tellraw` line passed for Steve's chat. `/msg`, `/me`, `/say` and `/teammsg` from clients that do not sign chat, such as bots, arrive without a UUID; the bot then takes the player's UUID from the hover the server puts on the speaker's name, so they are still that player's. A speaker whose UUID is not in the player list is shown as `"Steve" (unlisted)` and is not triaged. On a server whose plugin resends players' chat as system messages, that chat is now only `[system]` lines: it is not triaged and cannot give chat commands; before, chat triage and chat commands read it by its text. The descriptions of `read-chat`, `get-events` and `wait-for-event` say that player text is untrusted.
- The bot no longer says "LLM-powered bot ready to receive instructions!" in public chat when it joins the world; by default it says nothing. `--greeting <text>` gives it a line to say each time it joins (not when it respawns). The text must be one line of plain chat of at most 256 characters that does not start with `/`; otherwise the server writes one line to stderr and exits with 1.
- mineflayer 4.39.0, mineflayer-pathfinder 2.4.5 and minecraft-data 3.117.0 are pinned to exact versions, and the package carries `npm-shrinkwrap.json`, so an install from npm gets the dependency tree that was tested.
- The package holds only the built JavaScript, `package.json`, `npm-shrinkwrap.json`, the READMEs, the license and this changelog. The MCP server reports the version from `package.json`.
- The link at the end of a connection error points to Getting started in this fork's README.
- Commands that drive the bot's body (moving, digging, placing, attacking, using items and the like) stop after about 50 seconds, before an MCP client's usual 60-second request timeout, and the reply says where the bot stopped. Tools that do not drive the body (queries, `wait-for-event`), `collect-block` and `lead-animal` are not stopped at 50 seconds.
- The long tools reply within that limit by themselves and leave long work to the background. `collect-block` and `lead-animal` wait at most about 45 seconds for their task: a task still going then keeps running, and the reply is a success, `Still collecting after 45 s: task t5 gather keeps running in the background (…). Wait for it with wait-for-event types ['task_done', 'task_failed', 'task_cancelled'] (list-tasks shows whether it has already ended); stop it with cancel-task t5` (`Still leading after` for `lead-animal`, `is paused (<reason>)` for a paused task); before, they waited until the task ended, a held task until its time limit. Their `timeoutMs` still limits only the task, and when `timeoutMs` plus 5 seconds comes before the reply is due, a task that never got to run is still cancelled then (`time limit reached`); otherwise it stays queued and the reply says it `is paused`. `move-to-position` and `goto-waypoint` stop after about 35 seconds unless given `timeoutMs` (before, they had no limit), and the error says where the bot stopped, how far from the target, and to call the tool again. `clear-region`, `fill-region` and `dig-tunnel` stop after about 45 seconds instead of 120, with the same counts as before. `smelt-item` waits at most about 45 seconds, and when items are left the reply says that the furnace keeps smelting them. `move-in-direction` cuts a longer `duration` to about 45 seconds and says so. A `timeoutMs` given to the moves, the region tools or `smelt-item` is kept and lengthens the call's limit; the MCP client must then wait that long. The tool descriptions give the new defaults.
- `--call-limit-seconds` (a whole number from 20 to 3600, default 50) sets the call limit, for MCP clients that wait longer than 60 seconds for a reply; the defaults above grow with it. A value outside the range writes one line to stderr and exits with 1.
- An action that did not happen now returns an error (`isError`, the text starting with "Failed: ") instead of a plain reply: `place-block` into the bot's own cell, into a cell that already holds a block, or with nothing to place against; `dig-block` on a block that is not loaded; `smelt-item` without a furnace, input or fuel, with a furnace slot in the way, or with no output in time (that reply now also says the input and fuel are in the furnace, and where); and `equip-item` with an item that is not in the inventory. Queries that find nothing and requests for a state the bot is already in (`unequip-item` on an empty slot, `wake` when not sleeping, `dismount` when not riding, `dig-block` on air) are still plain replies. `place-block` no longer takes cave air or void air for a block in the way, and `dig-block` treats them as air.
- `fly-to` works only in creative and spectator mode, and its description says so: in another mode it returns an error and does not move the bot. Before, its creative check never fired, and in survival the server pulled the bot back or kicked it for flying. A flight that ends more than 1.5 blocks from the target, because the server pulled the bot back (for example at a block in the way), is now an error that says where the bot ended up, instead of a success.

### Fixed

- A connection attempt that fails before the bot joins now ends, instead of leaving the server "connecting" until it restarts.
- The pathfinder opens and closes wooden doors, keeps away from lava, and does not dig through built blocks or place scaffolding next to them.
- `place-block` picks a spot to stand on from which the block can be placed.
- `smelt-item` takes out all of the furnace's output, and first takes back a different fuel left in the furnace.
- `dig-block` picks a suitable tool and waits long enough for blocks that need an iron pickaxe or better.
- Body commands stop and say so when the bot dies.
- A body command that the MCP client cancels stops the bot at once; before, the bot kept walking toward the old target. The client drops the reply to a cancelled request, so a `command` event says what was cancelled and where the bot stopped. A cancelled `collect-block` or `lead-animal` cancels its task.
- A body command that is running when the bot leaves the game (kicked, or the connection is lost) returns at once with an error that gives the reason, for example "Kicked by an operator"; before, it did not return until the MCP client gave up. The next tool call reconnects.
